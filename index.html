How this works

A GLB file is a binary container: a 12-byte header (magic number 0x46546C67), a JSON chunk describing the scene graph, materials and accessors, and a BIN chunk holding the raw bytes — vertex data and textures — that the JSON's bufferViews point into.

This tool only touches the byte ranges that images[].bufferView point to. Identical images — common when several materials reuse the same texture — are written once and shared by every bufferView that pointed at them, whether or not they're also resized. A texture already at or under the selected max dimension is left completely untouched: a browser's built-in PNG encoder compresses more weakly than the native tools desktop apps use, so re-encoding a texture that doesn't need resizing tends to make it larger, not smaller — the original bytes already win. A texture over the max dimension is decoded, scaled down, and re-encoded losslessly (dropping the alpha channel only when every pixel in it is fully opaque, which loses no information). Every accessor, mesh, material, node and animation keeps its original index and its original bytes, so geometry is bit-for-bit identical and per-part materials stay separate.

Because the result is a .glb and this page can only hand you files in a fixed set of formats, the download arrives as a .zip containing the single .glb file — unzip it to get your optimized model.

Supports standard single-buffer embedded GLB files. Textures stored via extensions this tool can't decode (e.g. Basis/KTX2) are deduplicated by content but left unresized.
